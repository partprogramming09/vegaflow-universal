# Verification status (2026-11-05; last updated 2026-11-22)

**In short:** not everything the code does has been measured. This page lists what was proven on the test laptop, what was not, and the known defects. For example, the UMA preset raises the average FPS of Octopath Traveler II's open world from 30.29 to 42.89 (+42%, interleaved, 2026-11-22), and all of that gain comes from its 18 visual-quality cuts, not from the streaming or AsyncCompute lines.

**Reader:** people

The earlier sections of the guides describe what the code does and the intent of each optimization. Not everything has been measured. Measurements were taken with `scripts/bench.ps1` (PresentMon, a tool that records each frame the game shows) and with interleaved A/B testing in ABBA order (the runs alternate A, B, B, A so that drift over time cancels out). Details are in [`2026-11-ab-daemon.md`](./2026-11-ab-daemon.md) and [`2026-11-base.md`](./2026-11-base.md).

- **Removed because they cost measured performance:** `CPMINCORES=100` in the APU profile (the core-parking setting for the minimum number of cores kept awake; −21% in `drawstress` D3D11) and confining the game to 8 of 12 threads (between −19% and −24%). The second is now the option `restrict_game_cpu_sets`, off by default.
- **No measurable effect in `drawstress`:** `Win32PrioritySeparation` (a Windows setting for how much CPU time the foreground app gets), PCIe ASPM, EPP and the boost mode (≈1%). The 0.5 ms NT timer that another process requests does not change `Sleep(1)` in a third-party process.
- **Proven gain:** isolating background processes while the game runs unrestricted. With a heavy background load (Chrome with no window, 6 workers), `drawstress` goes from 51.0 to 109.3 FPS in D3D11 and from 39.5 to 90.0 in D3D12 (2.1 to 2.3 times). With 2 workers the gain is +13% average FPS and does not improve the lows; without background load it is zero. Almost all of it comes from confining the background to a few threads (+98% isolated). EcoQoS adds 11%, and I/O priority does nothing under this load. This is a worst case with a single synthetic load. The gain scales with the load: +14% with 1 worker, +45% with 4, and 2.1 times with 6. The daemon confines the background only when it uses at least 0.5 logical processors, and releases it below 0.25. Below 0.5, confining does not help; in D3D11 at 0.23 it cost 5%, while in D3D12 it does not cost anything. With a 4-worker load the daemon keeps the gain over 5 and 10 minutes (+51% FPS, about 300 MHz more effective CPU speed) at the same ACPI temperature (81 to 83 °C in the 5-minute series and 82 to 85 °C in the 10-minute captures, both in [`2026-11-ab-daemon.md`](./2026-11-ab-daemon.md); the laptop sits at its thermal limit either way). Without load nothing changes. Confining also protects against a load that saturates memory (+59%).
- **Threads for the background:** one full physical core (with its SMT, or hyper-threading, sibling threads) when the machine has 4 or more cores, and a single thread with fewer. Measured by simulating affinity (which cores a process may use) at 4, 6, 8 and 12 threads; 16 threads or more is an extrapolation.
- **Real game (Octopath Traveler II, D3D11, 120 s per capture, 5 or more captures):** the UMA preset in `Engine.ini` (Unreal Engine's config file) gives +40% average FPS in the world (43.15 against 30.72, not interleaved). Superseded on 2026-11-22 by the interleaved, per-factor measurement below (F2.4): the gain comes from the visual cuts, not from the streaming keys. The daemon changes nothing without background load or with a realistic background mix. With 4 Chrome workers in the world it gave +34% (old method). In the menu, limited to 60 FPS, it cut late frames from 1.8% to 0%. GameDVR (Windows' game recording feature) has no effect. Noise between launches: 0.23% (FPS) and 0.41% (1% Low). The daemon at rest uses 1.8 MB of private memory, with no leak over 6 open-and-close cycles. Known defect: killing the daemon by force leaves the registry and the confinement applied, and they can be recovered with `--restore-registry`. Details in [`2026-11-base.md`](./2026-11-base.md) and [`2026-11-ab-daemon.md`](./2026-11-ab-daemon.md).
- **Octopath without SCSKiller (2026-11-09, interleaved A/B, 3 × 120 s):** with 4 Chrome workers the daemon gives +36% average FPS and +30% 1% Low. **Without load the 1% Low drops ≈ 6%** (the average is the same), and the game moves from Legacy Flip to Independent Flip (two ways Windows presents frames to the screen). Without background load the game's HIGH priority adds nothing over Normal (with load, and not isolated). This is the cause of the regression without isolation. Details in [`2026-11-09-diagnostico-laptop.md`](./2026-11-09-diagnostico-laptop.md).

- **Known cautions:** the C++ suite makes real changes, but a final guard returns the power plan and the registry to their previous state (checked 2026-11-21: 405/405, and `tweaks_state.ps1` shows every value at its factory setting afterwards). Since F1 (PR #21), giving back ("Restore all", end of a game session, daemon shutdown) only restores VegaFlow's saved copies and writes nothing when there is no copy; turning a switch off by hand in Settings writes the Windows default only after saving a copy. A restore that Windows refuses stays pending in the change journal instead of being marked as restored. `SetApuPowerMode`, and the changes to GameDVR, the AMD driver, MPO, MMCSS (the Windows service that gives priority to media and game threads), `Win32PrioritySeparation` and `DisablePagingExecutive`, save the original value (`SOFTWARE\VegaFlow\RegBackup`) and restore it. `vegaflow_daemon.exe --restore-registry` returns all of them. The daemon restores the registry when it closes normally (checked: after stopping, the registry matches the state before it started). On Windows in Spanish, use SIDs in `icacls` (the Windows command for file permissions) and `WindowsBuiltInRole::Administrator`, because English names fail silently.
